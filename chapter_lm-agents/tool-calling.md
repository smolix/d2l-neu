**Idea:** A tool call is a structured assistant turn in the chat template and the tool's answer is another turn, so calling a tool is text generation and its accuracy is measured like any other output.
**Opening:** The chat model of Chapter 1 multiplies a three-digit number by a two-digit number and gets it wrong, and when asked to use a calculator it writes something no program can parse. The concrete example is the opening cell: 200 seeded products, Qwen3-1.7B with and without a calculator reachable through `d2l.tool_chat`, exact-match accuracy, the prompt-token overhead of the schema, and one rendered prompt. The open question: once the call parses and the tool answers, how far should the model trust the text that comes back?
**Teaches:**
- The tool turn: a JSON schema per function rendered into the system prompt by the chat template (the `tools` argument of `apply_chat_template`), the call emitted as text inside `<tool_call>` (Qwen3) or as `<function=name>` with `<parameter=key>` lines (Qwen3.5), parsed by a parser that returns errors instead of raising, and the result returned as a tool turn; parallel calls as several blocks in one turn, dependent calls as two rounds; `tab_lm_tool_formats` with the two formats, their thinking defaults and their vocabularies.
- The error taxonomy (`tab_lm_tool_errors`): no call, spurious call, syntax, truncation, unknown tool, schema, value, wrong selection, wrong count, execution; which errors the harness returns to the model as an `Error:` tool message with one retry.
- Training data for tool use: synthetic traces kept only if they execute (three verification stages: format, execution, semantic), the trace mix (single call, parallel, dependent, abstention, error recovery); Toolformer's self-supervised insertion in one sentence and Gorilla's retrieval-aware API calling in one sentence (historical); the current signal is agentic RL (10.4) and synthetic traces at scale.
- MCP as the protocol between models and tool servers: JSON-RPC 2.0 with `initialize`, `tools/list` and `tools/call`, a 30-line server and client, the printed token cost of 20 tool descriptions; one sentence on governance: MCP was donated to the Linux Foundation's Agentic AI Foundation in December 2025 together with AGENTS.md and goose.
- Accuracy by name, by arguments and by execution, on a BFCL-style set with intervals clustered by function name.
**Derivation:** none as a section result; two small ones with check cells. Toolformer's filter is a thresholded weighted log-likelihood ratio: keep a call if min(L(none), L(call text)) minus L(call and result) is at least a threshold, with the extra baseline ruling out gains from the call text alone; checked on 30 seeded arithmetic sentences with Qwen3-0.6B (a correct result gives positive gain, a corrupted one negative; sign fractions with a bootstrap interval). The per-turn SFT samples equal the masked full-sequence loss exactly when the template is prefix-stable; checked in fp32 on one trace with Qwen3.5-0.8B (agreement to 1e-4 relative, token equality of the two renderings) and shown to fail for Qwen3-0.6B (token sequences differ, loss gap printed).

**Writer notes:**
- The model has no tool API, only a text convention; the schema's token cost is paid every turn, and a tool that returns 50 KB is a context bug. Results come back as user turns, so result text can be mistaken for instructions (10.5 owns the attack).
- The wrong parser silently returns no calls; `tab_lm_tool_formats` and `d2l.parse_tool_calls(fmt=...)` make the choice explicit. BFCL names contain dots and types like `dict`, `float`, `tuple`; convert to JSON Schema (`object`, `number`, `array`).
- Narrow tool fine-tuning can raise the spurious-call rate on irrelevance items (over-calling); report `E_SPURIOUS` next to accuracy. Greedy decoding hides sampling variance, not batch nondeterminism.
- Reference implementations: Transformers `get_json_schema` and, where it exists in the pinned release, `tokenizer.parse_response` (skip with a printed note otherwise); vLLM's `--enable-auto-tool-choice --tool-call-parser hermes` for Qwen3 as the production parser, counting how many of the 450 generations it reads differently; `bfcl-eval` for scoring. Do not copy BFCL leaderboard numbers; the subset scores are not comparable (sampling, prompt format, AST-only).
- MCP: pin the specification revision (2026-07-28 resolved on 28 October 2026) and the `mcp` package major version; the from-scratch server and client are the fallback if the SDK API moved. The governance sentence cites the AAIF announcement (primary); tool poisoning through descriptions is one sentence here and 10.5's subject.
- Library additions (signatures): `d2l.parse_tool_calls(text, fmt='qwen3', schemas=None) -> (text, list[ToolCall])`; `d2l.ToolRegistry` with `.add(fn)`, `.schemas`, `.execute(call) -> str` (validates, runs, truncates to 2,000 characters, never raises), `.log`; `d2l.tool_chat(model, tokenizer, messages, registry, fmt='qwen3', max_rounds=4, enable_thinking=False, **sampling)`; `d2l.turn_samples(messages, tools, tokenizer, fmt)` (also 10.4's oracle); `d2l.load_bfcl(category, n=None, seed=0, revision=...)`; `d2l.make_tool_traces(n, seed, families=...)`.
