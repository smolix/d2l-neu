**Idea:** A configuration file determines a model's parameters, active compute and cache bytes per token, and a technical report is read against those derived numbers rather than taken on its word.
**Opening:** The configuration files of Qwen3-0.6B and Gemma 4 E2B do not yield their cards' parameter counts from the obvious fields, and the opening cell shows why: flattening the Qwen3-8B and DeepSeek-V4.1-Flash configurations gives 26 keys against 87, and one repository carries three "parameter counts" (a 552B backbone in the report, 763,205,315,794 elements in the safetensors index, and the 12 L d-squared count), none of which agree, each right for a different question. The open question: what does a report leave out, and how would the reader notice?
**Teaches:**

**Writer notes:**
- "Parameters" has at least five meanings (total, active, backbone, checkpoint elements, bytes); say which every time. The Hub API counts packed fp4 and MXFP4 tensors as elements while the header gives the packed shape; an "off by two" is almost always this (gpt-oss's U8 tensors). Lookup tables (Engram) cost memory and traffic, not FLOPs: V4.1-Flash holds 196.6B elements of tables beyond its 552B backbone. `num_key_value_heads` is meaningless for MLA (128 in V3) and 1 for V4's single KV head; cache bytes come from `kv_lora_rank` plus `qk_rope_head_dim`, or from `head_dim`. `mla_use_nope` does not remove the rope slots from the weights; read shapes. A configuration can lag its report or its weights; print disagreements, never tune. Do not infer a mechanism from a field name: `hc_mult` is the number of residual streams, `compress_ratios` is per layer with extra entries for MTP slots (43 entries for 40 layers).
- Differences from the blueprint: the lookup-memory axis is separate from the feed-forward axis; the DeepSeek line gains the V4 step (the blueprint already added it as a fifth row); Gemma 4 E2B and 26B-A4B, Qwen3.6-35B-A3B and Qwen3.8-27B join the core rows; Kimi K3's disputed active count is a configuration-derived entry; the capstone's `comparators(scenario)` reads this table.
- Library additions: `d2l.config_stats(config, *, kv_bytes=2, state_bytes=4, groups=('text',), plan=None) -> d2l.ConfigStats` (fields `total_params`, `active_params`, `params_by_group`, `flops_fixed`, `flops_per_ctx_token`, `cache_bytes_per_token`, `cache_bytes_bounded`, `state_bytes`, `layers`, `notes`; methods `flops_per_token(ctx, mode)`, `cache_bytes(ctx)`, `to_row()`); `d2l.LayerSpec` (mixer in `gqa`, `swa`, `mla`, `dsa`, `gdn`, `kda`, `lightning`, `csa2`; ffn in `dense`, `moe`, `latent_moe`); `@d2l.register_arch(model_type)` registering a plan of at most 30 lines (the only model-specific code; registered plans listed in blueprint ch14 §14.1, to which `gemma4` is added); `d2l.load_config`, `d2l.safetensors_census`, `d2l.design_table(registry, core_only=True)`, `d2l.ReportSchema`, `d2l.check_report`. An unknown field with no mapping is appended to `notes`, never guessed.
- Risks and fallbacks: a renamed or gated repository keeps its pinned snapshot; packed-dtype unpack factors differ per format (one test each; unresolved cases go to notes and leave the exact-match set); the 68-byte indexer layout is an assumption to revise if the V4 report contradicts it; `config_memory` and `config_stats` disagreeing is filed with 1.1, with `config_stats` authoritative per layer kind; Qwen3.8-Flash-Next has no report and stays a configuration-only row.
