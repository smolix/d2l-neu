**Idea:** The same recipe scales from one GPU to a node by sharding the frozen weights and the adapters, and a toolchain is that recipe written as configuration, to be checked against the from-scratch oracle.
**Opening:** A 27B model is 54 GB of bf16 weights; sharded over eight 40 GB cards, LoRA fits with room to spare, full fine-tuning does not fit at all, and a ledger says so before any GPU is rented. The reader derived ZeRO-3's bytes per rank in Advanced and ran FSDP in 6.2; here the frozen weights, the quantized codes and the adapters are the state being sharded. The closing question is what changes when the model fits no node, which the same ledger answers for a mixture of experts.
**Teaches:**
- LoRA and QLoRA under FSDP2: frozen weights sharded like any state and all-gathered per layer every step (LoRA does not remove that traffic), fp32 adapters sharded or replicated, the per-GPU ledger $M = (b_w P_{\textrm{lin}} + 2P_{\textrm{rest}})/N + 16 P_a / N_a + k_g W_{\max} + W_{\textrm{emb}} + A + \Lambda$ with the gathered working set and boundary activations, and the all-gather and reduce-scatter times from the link bandwidth; `min_gpus` for a model, method and card size.
- QLoRA's codes under sharding: packed 4-bit codes viewed as bf16 for the sharder and re-viewed as bytes after the gather (the shard-safe mode of `QuantLinear`; the quant-storage trick), double-quantization state replicated, weight traffic cut about 3 times (not 4, because embeddings and head stay bf16), which turns QLoRA into a speed argument on PCIe-only nodes.
- Full fine-tuning at scale as arithmetic: 16 bytes per parameter makes 27B need 18 cards of 40 GB or 7 of 80 GB; ZeRO-3 with CPU offload of optimizer state puts 4 bytes per parameter on each GPU and 12 on the host (323 GB for 27B), costed and not run; the 8B full fine-tuning calibration arm.
- Toolchains as the recipe in configuration: one recipe (LoRA rank 16 on all linear layers, AdamW, linear warmup and decay, an effective batch of 8 rows of 1,024 tokens, token-mean loss over the effective batch) expressed in PEFT with TRL and in torchtune, with Unsloth, Axolotl and LLaMA-Factory named as configuration-driven wrappers run from committed scripts; library defaults that differ (clipping, warmup rounding, loss normalization) found by bisection against the oracle's first 20 losses; configuration files as the experiment record; where throughput differences come from (fused cross-entropy, attention backend, packing, checkpointing, compilation).
- Past one node: the same ledger for a mixture of experts read from a released configuration (Qwen3.5-397B-A17B, header only): which modules carry adapters (attention, shared experts, routed experts), why adapters on routed experts multiply adapter memory by the expert count while each token trains only the experts it reaches, frozen routed experts placed by expert parallelism (6.6) rather than gathered by FSDP, QLoRA's bytes and the node count they save, and optimizer-state offload costed; hosted trainers run this same recipe, said in one sentence.
**Derivation:** none beyond the accounting identities (the per-GPU ledger above specializing 6.2's FSDP memory; the effective batch $E = b \cdot k \cdot p$ rows with steps $\lfloor n / E \rfloor$ and the off-by-one of warmup rounding, $\eta / S$ per step, 5% at $S = 20$). Smallest case: Qwen3.6-27B-class at $N = 8$: bf16 weight shard 6.72 GB, NF4 shard 2.21 GB, sharded adapters 0.23 GB, gathered working set 4.84 GB (bf16) or 3.31 GB (NF4), boundary activations 1.34 GB, totals 13.1 GB (LoRA) and 7.1 GB (QLoRA) before layer internals and NCCL; full fine-tuning 60.7 GB. The notebook checks the ledger against `max_memory_allocated` per component group at $N = 1$ (T1), $N = 2$ (T2 pair) and $N = 8$ (T3) within 15% with the residual explained.

**Writer notes:**
- Model choice: Qwen3.6-27B (Apache-2.0, verified on the Hub) is the target and Qwen3-32B the fallback (the blueprint names Qwen3.8-27B, whose licence is not stated in its README, so it is used only if confirmed on the weights page). The blueprint's layer-by-layer parameter accounting (64 layers, hidden 5,120, 48 Gated DeltaNet plus 16 full-attention layers, vocabulary 248,320) was read from Qwen3.8-27B's configuration; the author re-reads Qwen3.6-27B's configuration and re-derives the ledger before writing any number.
- Kernel tiers for the hybrid: Hub kernels, then `flash-linear-attention`, then the pure-PyTorch chunked delta rule (correct, slow, memory-hungry, rejects packing; a warning in the log means kernels were not used). Check in order: kernel against reference at T1, one-rank FSDP2 at T1, two ranks on the T2 pair, then T3; any failure, NaN in the delta-rule layers, or a first step far from the ledger triggers the fallback. The mixed-precision policy must not cast the fp32 `A_log` and gated-norm parameters.
- Silent breakages: every rank loading the full checkpoint (8 times 54 GB); `reshard_after_forward=False` keeping a full extra copy; the embedding and head at vocabulary 248,320 (2.5 GB each) and logits returning if the loss is not chunked; mixed dtypes in one FSDP unit (the shard-safe view exists for this); comparing losses across arms with different masks or batches; one `nvidia-smi` reading instead of `max_memory_allocated`, the snapshot and the topology; merging a 27B LoRA needs about 54 GB of host RAM, out of band.
- Toolchains: the book environment runs the oracle and PEFT with TRL; Unsloth and Axolotl cap `torch` below the book's pin and torchtune is unmaintained (README banner), so those arms run from committed scripts in their own environments and are read from logs (decided 2026-10-29); the comparison in prose is limited to PEFT with TRL and torchtune, with Axolotl 0.21 named as the active alternative for the editor's call; `template: qwen3` in LLaMA-Factory and friends must be checked token for token against `render_chat`; Unsloth's patches change numerics, so the tolerance band is measured from three adapter seeds, never bitwise.
- Past one node: the mixture-of-experts ledger is arithmetic on a released configuration (Qwen3.5-397B-A17B, Apache-2.0, about 403B parameters; header read by range request), checked by summing the header's element counts per group; report the routed experts' share of parameters, and state that the expert-parallel placement is 6.6's and is not re-derived. Hosted fine-tuning is not taught: one sentence says that hosted trainers (Tinker is cited) run this recipe and leave the data, the mask, the rank and the learning rate to the user.
- Do not re-teach: ZeRO stages and FSDP's life cycle (`sec_multi_gpu_concise`, 6.2), the memory ledger (7.1), the quantizers (7.5), the landscape (`sec_training_systems`). New here: sharding frozen and quantized state, the per-GPU ledger with communication, the shard-safe codes, the oracle-against-library protocol, the past-one-node ledger for a mixture of experts.
