**Idea:** Decoding attends with one query per head, so a kernel that gives each head one thread block leaves most of the GPU idle at a long context; splitting the cache across blocks and merging their softmax statistics reads the cache at full bandwidth.
**Opening:** The reader has 12.1's decoder at a stated fraction of the bound for a short prompt. The opening cell times one decode step of Qwen3-0.6B at batch 1 and contexts of 512, 8,192 and 32,768 tokens with the scaled-dot-product kernel, prints the bytes of cache read per step from the ledger, and shows that the attention kernel's share of the step grows from negligible to most of it while its achieved bandwidth is a small fraction of the GPU's. The question is why reading 0.9 GB of cache takes many times longer than reading 1.2 GB of weights, and the closing question is what the kernel must do when the cache is not one contiguous slab.
**Teaches:**
- The shape of decode attention: queries `[b, H_q, 1, d]` against a cache `[b, H_kv, L, d]`; the grid of a FlashAttention-style kernel is `b × H_kv` blocks, so at batch 1 Qwen3-0.6B's eight KV heads occupy eight of 128 streaming multiprocessors; the achievable bandwidth from a few blocks is a fraction of the device's.
- Split-KV (Flash-Decoding): partition the `L` axis into `s` chunks, run the online-softmax accumulator per chunk in parallel, write one `(m, l, o)` triple per chunk, and merge with the same rescaling rule that `sec_attention-at-scale` used across tiles; choosing `s` from the batch, the KV heads and the SM count; the merge's extra traffic (`s (d + 2)` floats per head).
- GQA packing: the `g` query heads that share a KV head become the row dimension of the tile, so the KV bytes are read once per group instead of once per query head; why this matters for bandwidth at `g = 2` and more for `g = 8`.
- The Triton kernel: the one cell allowed over 30 lines; program ids over `(batch, KV head, split)`, a loop over key blocks with the running maximum, a store of partial statistics, and a small merge kernel; masking at `kv_len` so padded columns contribute nothing.
- Reading from pages: the same kernel with a block table indirection (`physical = table[j // B]`), which is what Chapter 13's paged cache needs; the cost of the indirection against a contiguous slab.
- Production kernels as the oracle and the measuring stick: `flash_attn_with_kvcache`, FlashInfer's plan-and-run interface (fixed-shape graphs with variable lengths, its own split heuristics), and what each adds beyond the notebook's kernel.
**Derivation:** Bandwidth as a function of parallelism. If one thread block sustains at most `β_1` bytes per second and the device `β`, a grid of `p` blocks reads at `min(p β_1, β)`, so the cache read takes `b L k_KV / min(p β_1, β)` with `p = b H_kv s`; the splits needed to reach the device bandwidth are `s ≥ β/(b H_kv β_1)`, and the merge adds `s H_kv (d + 2)` floats of traffic, negligible while `s (d + 2) ≪ L d`. Smallest case: `b = 1`, `H_kv = 8`, 128 SMs, `β_1 ≈ β/128`: sixteen splits fill the device; at `L = 8,192` and `d = 128` the merge traffic is below 0.01% of the cache bytes.

**Writer notes:** The kernel is the lesson; keep it readable (program ids, a loop, a store, a merge) and put every optimization that is not the idea (tile tuning, software pipelining) into one sentence and a pointer at FlashInfer. Masking: a row's valid keys end at `kv_len[row]`, and splits that fall entirely past it must write `m = −inf, l = 0` so the merge ignores them; a test with ragged `kv_len` catches the off-by-one. GQA packing requires the `g` query heads of a group to be contiguous in memory; 1.2's `Qwen3Attention` layout satisfies this, and the test checks the head order. Triton version: pin it; the kernel compiles per `(block size, d)` and the first call's compile time is excluded from timing. Float32 accumulation of `l` and `o` with BF16 loads; a BF16 accumulator fails the tolerance at long contexts and the notebook shows it once. The split count must not depend on the batch composition if 12.3's determinism is wanted: use a fixed split size (so the number of splits depends on `kv_len` only), and say so here in one sentence, since 12.3 builds on it. FlashInfer and `flash_attn` wheels may be absent on the build image; both rows are optional and silently omitted. On the A100 (T2, optional) the bound line changes to 1,555 GB/s and the SM count to 108. Do not re-teach: online softmax, GQA, CUDA graphs.
