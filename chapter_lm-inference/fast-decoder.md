**Idea:** A decode step is a stack of small kernels, and its gap to the bandwidth bound is launch overhead between kernels, bytes read that were never needed, and weights stored in more bits than the kernel needs.
**Opening:** The reader runs `generate_cached` from `sec_kv-cache` on Qwen3-0.6B and sees a few hundred tokens per second against the bound of about 840 computed from 1.19 GB of BF16 weights at 1 TB/s. The opening cell prints that ratio, then two numbers from a ten-step profile: kernel launches per step and the fraction of wall time during which the GPU ran anything. The question is where the rest of the time goes, and the closing question is what happens when a second request wants the same GPU.
**Teaches:**
- The bytes ledger of one step: every tensor read once (the blocks, the tied matrix read as the head, the norms) plus `L` times the KV bytes per token; the ledger as a table over weight formats and context lengths, and the ceiling it implies; the kernel census from the profiler as the to-do list.
- A static cache with position tensors: a contiguous slab per slot, positions as device tensors, the mask `j ≤ kv_len + t`, padded prefill with per-row positions; one primitive `forward(tokens, pos)` that serves prefill (`T = n`), decode (`T = 1`) and later verification (`T = γ + 1`).
- CUDA graphs for the decode loop: what a decoder adds to `sec_compilation` (all state static, no host synchronization in the step, graphs keyed by batch and length bucket); manual capture against `torch.compile(mode='reduce-overhead')`; sampling outside the graph; the cost of a host read every step.
- Wasted bytes: a static cache read to its maximum length pays for columns that hold nothing; length buckets restore the `W + L k_KV` line, at the price of one graph per bucket.
- Fewer bytes: weight-only int8 and int4 through a kernel that dequantizes in registers (tinygemm; Marlin as the one-difference relative that stays near its byte ratio to larger batches); why quantizing only the blocks caps the gain (the tied head is 26% of Qwen3-0.6B's bytes) and what quantizing the head costs in quality.
- From one stream to many: throughput against batch size for the same decoder, against the hardware chapter's step-time model, as the hand-off to Chapter 13.
**Derivation:** Launch overhead against kernel time. With `n` kernels of GPU durations `g_i` enqueued every `c` seconds, the step ends at `T = max_i (i c + Σ_{j ≥ i} g_j) ≥ max(Σ g, n c + g_n)`; in the regime `n c > Σ g` the step is CPU-bound and graph replay removes about `n(c − c_g)`; in the other regime graphs change nothing. Smallest case: 20 kernels of 10 µs each with `c = 8 µs` (GPU-bound) against the same with `c = 20 µs` (CPU-bound). Second, short: Amdahl's law for bytes, the speedup `1/((1 − f) + f/r)` when a fraction `f` of the bytes is compressed by `r`; for Qwen3-0.6B int4 on the blocks alone gives 2.19 times at zero context and 1.70 times at 8,192 tokens of cache.

**Writer notes:** "Graphs make kernels faster" is wrong; they remove gaps, and if the GPU-busy fraction was near 1 nothing changes (the derivation's GPU-bound regime). A graph that captured a Python integer (the position, the length) replays the stale value forever; positions must be device tensors, and a test advances the position across three replays and checks the written cache column. Time with `torch.cuda.synchronize()`; separate first-request latency (compile plus capture) from steady state and report both. A forgotten `contiguous()` on a sliced cache view copies the cache every step (the `sec_kv-cache` leak, now as bandwidth); the profiler check catches it. Quantizing `lm_head` of a tied model quantizes the embedding unless the tie is broken; `quantize_head=True` must untie explicitly and the test checks the embedding lookup is still BF16. Transformers `generate` does more work per token (processors, EOS checks, host syncs) than a bare graph loop; the first stage's row says what each loop does. torchao's int4 layout API changes between releases (`Int4WeightOnlyConfig` or its successor; `_weight_int4pack_mm`): check at authoring, fall back to the reference dequantize-then-matmul path for correctness and a Marlin repack for speed, and if neither runs on Ada report int8 only with int4 as a ledger prediction, labelled. Compile times of one to three minutes can break the 12-minute budget: cache inductor artifacts through `d2l.DATA_HUB` or take the compile row from the committed table and say so. The reference implementation for every variant is the float32 eager `FastGenerator`; tolerances as in step 2; the 98% top-1 agreement line for BF16 variants is a screening threshold, not a result, and int4 may fail it (the table says so).
