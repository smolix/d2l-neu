**Idea:** A configuration is a mesh over the data, tensor, pipeline, context and expert axes mapped onto the links of a cluster, and a cost model built from the five sections' formulas ranks the feasible configurations before any of them runs.
**Opening:** The reader has one formula for memory and one for bytes per step from each of 6.2 to 6.6 and the link numbers of Chapter 5. One concrete example: Qwen3-8B on sixteen GPUs admits 35 ordered factorizations of the world size over four axes; most do not fit 40 GB, and among those that fit some are three times slower than others. The open question: whether a cost model composed from the parts predicts the measured order, and where it is wrong.
**Teaches:**
- The mesh: named axes, their order, which axis spans which link; placement by exposed volume (the axis with the largest exposed bytes on the fastest link); the common order (TP innermost, then CP, PP, data parallel outermost) as an outcome, not a law, and when it flips.
- Feasibility: memory per GPU from the five `*_costs` functions, microbatch counts from the global batch, divisibility; `d2l.enumerate_configs` returns the feasible list and the rejected ones with reasons.
- The step-time model: compute at a GEMM efficiency measured per shape, the pipeline bubble from 6.4's simulator, one exposed term per axis from the alpha-beta fits, hierarchical sharding across nodes; MFU as a product of factors, each a bar of a waterfall; weak against strong scaling and the largest useful GPU count at a fixed global batch.
- The library landscape in two sentences with `tab_training_tools` linked; a TorchTitan recipe as the executable form of a configuration.
**Derivation:** Placement and the MFU waterfall (blueprint ch06 6.7 D1, D3). For axes with exposed volumes U_1 >= U_2 and links beta_1 >= beta_2, assigning the larger volume to the faster link is better by (U_1 - U_2)(1/beta_2 - 1/beta_1) >= 0, and adjacent exchanges extend it to n axes (the rearrangement inequality). With executed FLOPs rho_r Phi (rho_r = 4/3 under full recomputation), mean GEMM efficiency eta, bubble fraction b and exposed time T_exp, T_step = rho_r Phi / (N F eta (1 - b)) + T_exp and MFU = (eta (1 - b) / rho_r) / (1 + T_exp / T_compute), so MFU is bounded by eta (1 - b) / rho_r before any communication. Smallest numeric case: the number of ordered factorizations of 2^a into four factors is C(a+3, 3), 35 for 16 GPUs and 56 for 32, which `enumerate_configs` returns exactly without constraints.
**Notebook:**
1. Question: does the cost model's ranking of Qwen3-8B's layouts on two nodes agree with measurement, and does the measured MFU decompose into the predicted factors?
2. Calibration on one node (pre-registered before the two-node runs): the GEMM-efficiency table per shape (`lm-matmul-eff`), the overlap parameter from 6.2's sweep, the stage times from `lm-pp-calibration`; no parameter is tuned on the layouts it judges.
3. T0: `enumerate_configs` for 16 GPUs at a global batch of 512 x 4,096 tokens; `ParallelCostModel.rank` with the NVSwitch row and the PCIe-pair row; the top three, one predicted-slow layout, and one cross-node TP layout as the control.
4. T4 (committed bundles from one two-node allocation, about one hour): the chosen layouts run with TorchTitan (Qwen3-8B if the pinned recipe set supports TP, PP and CP for it, else the verified Llama-3-8B shape with the `ModelShape` printed), eight-minute runs; measured step time, MFU in both conventions, `exposed_comm`, per-rank timelines.
5. The waterfall: for each run, eta from compute-only kernels, b from the PP timeline, T_exp from `exposed_comm`; the product against the reported MFU (within 5%; a larger gap is attributed to the unmodelled remainder, named).
6. Optional: a four-node pass and one EP = 16 run of the 1.7B mixture (the one measured inter-node all-to-all point of 6.6).

**Writer notes:** Pitfalls (blueprint 6.7): tuning the cost model on the layouts it is then judged on (hence pre-registration and one-node calibration); mixing MFU conventions (causal attention counted or not, recompute counted or not, embedding and head included or not); comparing layouts at different global batches; a layout needing more microbatches than the global batch provides; reading a layout's MFU from one run on different nodes; treating "TP at most 8" as a law; forgetting the optimizer step, data loading and checkpointing in timed regions; believing the best layout at one scale is best at another. Risks: TorchTitan API and recipe drift (pin a commit; the verified Llama-3-8B recipe as fallback; the cost model takes whichever `ModelShape`); allocation size (core is two nodes for about an hour; the four-node pass and EP = 16 are optional, shown from a previous release's bundle with its date or omitted); gated Llama tokenizer (prefer the Qwen3 path); the cross-node TP run may fail for memory (short step count and a timeout); overfitting the model to the cluster (publish the residuals); TorchTitan's MFU convention differs (print both). The reference global batch of 2.1M tokens applies to 6.7 only and is four times the reference model's step; no claim about the critical batch of any model run here.
