**Idea:** Fully sharded data parallelism keeps every parameter, gradient and optimizer moment in one place and gathers each layer's weights just before it runs, so memory per GPU falls with the world size while the gathers must hide behind the previous layer's compute.
**Opening:** The reader derived the ZeRO stages in `tab_mgp-zero` and saw the FSDP life cycle in `fig_fsdp_lifecycle` without running it. One concrete example: eight ranks each hold an eighth of Qwen3-8B's 131 GB of training state and gather one block's 386 MB of bf16 weights before computing it; whether the next gather hides behind this block's compute depends on the tokens per GPU and on the link. The open question: what the peak memory per GPU is, term by term, and at what token count per GPU the communication becomes exposed.
**Teaches:**
- The `fully_shard` life cycle as a sequence of states per block (sharded fp32 parameters, gathered bf16 weights, local gradient, reduce-scattered fp32 gradient shard, sharded optimizer step), one block per group, the root group's exception (not resharded after forward by default), mixed-precision policy (parameters bf16, reduction fp32).
- The dials: wrapping granularity (one block, several, the whole model), forward and backward prefetch, `reshard_after_forward`, CPU offload, gradient accumulation without sync, global-norm clipping on shards.
- A from-scratch flat-parameter sharded layer (`d2l.FSDPLite`, about 110 lines in cells of twenty) that reproduces the library's bytes exactly in float64 on CPU, and the production recipe `d2l.fsdp_wrap` as one call.
- Memory and bytes per step as formulas with terms, checked against the allocator and against counted collective bytes; the critical token count T* above which the gathers hide, and why it does not depend on the model size.
**Derivation:** Peak memory per GPU and the critical token count (blueprint ch06 6.2 D1, D2). Peak memory is about 16P/k (state) plus (u_f + u_b) P_L (transient unsharded layers, u_f = 4 in forward with prefetch and u_b up to 14 in backward) plus the root group's bf16 weights and reduce buffer plus activations and logits; bytes per GPU per step are ((k-1)/k) (b_p P [1 + reshard] + b_r P), which is 8P (k-1)/k for bf16 gathers and fp32 reductions with resharding. The all-gather of block l+1 hides behind block l iff T >= T_f* = eta F b_p (k-1) / (2 (1 + eps_a) beta k), with eps_a the attention share; T* does not depend on P or L. Smallest numeric case: Qwen3-8B at k = 8 gives 16 x 8.19e9 / 8 = 16.4 GB of state per GPU, and at eta F = 200 TFLOP/s and the NVSwitch row's beta the forward threshold is a few thousand tokens per GPU (the cell prints the number for both `topo.txt` rows).

**Writer notes:** Pitfalls (blueprint 6.2): "16P/k is the memory" omits transient layers, the root group, logits and memory outside the allocator (NCCL buffers, the CUDA context); wrapping only the root gives one giant group and no overlap; `to_empty` without re-initialization; `reshard_after_forward=False` on every block defeats sharding in forward; gradient accumulation with sync disabled keeps full-size unsharded gradients; step times without a paired comparison; weight decay on norm weights inside a flat shard. Risks: `fully_shard` on gloo may be unsupported in the build image (T1 runs `FSDPLite` only and replays the bundle); Hugging Face meta-device initialization differs across versions (build the model as 1.2's `d2l.Qwen3GPT(**d2l.qwen3_gpt_kwargs(cfg))` instead); no headroom on 40 GB (fallback 4,096 tokens per GPU for the whole table); allocator fragmentation changes `reserved` but not `allocated`, report both; A100 has no FP8 and no FlashAttention-3, so SDPA's flash backend is the attention and anything FP8 in TorchTitan is off.
