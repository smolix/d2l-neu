# Serving Systems
:label:`chap_lm_serving`

The reader has :numref:`sec_lm_fast_decoder`'s decoder, which answers one request near the bandwidth bound. A service never sees one request: it sees an arrival process, a mix of prompt and output lengths, a latency contract, and a hundred users who are each waiting. This chapter builds the mechanisms inside a serving engine, each with an invariant a test can check and a measurement against a reference server, from the contract a service makes to the layouts that spread one model over a node.

Reference servers are vLLM and SGLang at pinned versions in separate virtual environments (their torch pins differ from each other and from the book's), reached only over HTTP through `d2l.OpenAIServer`; `LIVE_VLLM=False` replays committed curves. Every latency-throughput experiment reports a full curve over at least six offered loads that bracket saturation, with at least three arrival seeds, and pairs two systems on the same seed and requests; nothing is claimed from a single operating point. Traces: the Azure LLM inference traces of 2023 and 2024 (CC-BY), BurstGPT (licence read from its repository before any excerpt is committed), the Mooncake FAST'25 traces (conversation, tool-and-agent, synthetic; with block hash ids that 13.4 and 13.6 use), and ShareGPT token lengths only; prompts are seeded windows of the book corpus tokenized with the Qwen3 tokenizer so token counts are exact.
