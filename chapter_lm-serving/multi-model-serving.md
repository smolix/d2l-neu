**Idea:** Fine-tuned variants that share a base model can share one batch, because only a low-rank term depends on the request, and the cost of serving many adapters is bytes per distinct adapter, not arithmetic.
**Opening:** The reader has eight adapters from Chapter 7 on one base model and the opening cell prints the memory of eight full copies of Qwen3-0.6B, the memory of one base plus eight adapters, and the decode throughput of an engine that serves one adapter at a time by merging and unmerging as requests interleave: the adapters fit with room to spare, and the serial engine's throughput falls with the number of adapters in flight. The question is how many adapters one batch can carry and what it costs, and the closing question is whether a prefix computed under one adapter is worth anything to another.
**Teaches:**
- Why adapters share a batch: `y = x Wᵀ + s (x A_aᵀ) B_aᵀ`, with the base term identical for every token and the low-rank term per request; merged serving (free per token, one adapter per replica) against unmerged serving (an extra `r(d_in + d_out)` weights per distinct adapter in the step); which regime a traffic mix wants.
- Three ways to compute the batched term: grouped by adapter (two small matrix products per adapter segment; reads each adapter once), gathered per token (one launch, reads an adapter per token), and dense-masked (all resident adapters, two dense products); the production kernels (SGMV, BGMV, the engine's own) as fused forms of the first two.
- Adapters in the engine: an adapter id per token in the step batch, a pool of resident adapters as a cache with least-recently-used eviction and pinning for running requests, admission that waits for a slot, prefetch; Che's approximation (13.4) for the pool's hit rate; load stalls of 20 MB adapters against 350 MB ones.
- Cache correctness: any adapter changes every later layer's keys and values, so the prefix cache key includes the adapter (13.4's `key_prefix`), and a cache without it returns wrong activations, not stale ones; unified paging of adapter weights and cache blocks in one pool.
- Routing between models and cascades in one paragraph (a cheap model answers and escalates on a confidence signal; a router picks the model before generating), with the oracle bound and the random-mixing line stated and the evaluation left to an exercise.
**Derivation:** Bytes of heterogeneous batching. For one projection with `T` tokens, `A_dist` distinct adapters of rank `r` and `N` resident adapters, grouped batching reads `2 A_dist r (d_in + d_out)` bytes against the base's `2 d_in d_out`, per-token gathering reads `2 T r (d_in + d_out)`, dense masking `2 N r (d_in + d_out)`; over Qwen3-0.6B's seven projections at `r = 16` the grouped overhead is `0.0229 A_dist` of the base bytes, so grouped batching doubles decode bytes at about 44 distinct adapters, while serial merging costs about `A_dist` weight passes and loses for every `A_dist ≥ 2`. Smallest case: `T = 32`, `A_dist = 4`, `N = 16` ranked by bytes and launches.

**Writer notes:** Unmerged adapters are not free: at decode the cost is bytes per distinct adapter, and a per-token gather multiplies it by the batch. Merging is right when one adapter dominates a replica's traffic; batching is right for a long tail; the break-even is a traffic statistic, not a model property. Sharing a prefix cache across adapters returns wrong activations; adapter identity belongs in the key. Padding to `r_max` makes every adapter pay the largest rank's bytes; grouped kernels that handle ranks per adapter avoid it. The reference grouped mode is launch-bound for large `A_dist` and may look worse than dense masking for small pools; say so and name the fused kernel as the remedy rather than tuning the reference. If `lm-lora-r1-demo` is unavailable, train three one-epoch adapters (about two minutes each) for correctness and use random adapters for timing.
