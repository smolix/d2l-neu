**Idea:** Requests that begin with the same tokens at the same positions can share the blocks that store that prefix, so a prefix is computed once and the gain from caching is a property of the workload.
**Opening:** The reader runs 13.3's engine on a trace in which every request starts with the same 512-token system prompt and the opening cell counts prefill tokens recomputed: every request pays for the prompt again. The question is which requests may share a prefix and how to find it quickly, and the closing question is what happens when the shared blocks do not fit on the GPU.
**Teaches:**
- When two requests may share cache: same weights, same adapter, same tokens at the same absolute positions (keys depend on position through the rotary embedding, which a prefix satisfies by construction), same execution configuration (dtype, cache dtype, attention scheme); non-prefix reuse is not exact and is named as a pointer.
- The radix tree over page-aligned token runs: match walks from the root, insert splits nodes at page boundaries, running sequences lock their path, eviction removes unlocked leaves in least-recently-used order so a node outlives its descendants; block ownership (one reference from the tree, one per running sequence); the rules tests encode (a full-prompt hit is capped at `len − 1` because the last token's logits are needed; only full pages are cached; insertion after the step that computed the tokens, so two identical prompts admitted together do not share).
- Hash-chained blocks (vLLM) and token-level radix trees (SGLang) as the same trie at different granularity, with extra keys (adapter name, a cache salt) in the hash; cache-aware admission (order the waiting queue by matched prefix length with an aging term) against first come first served.
- The workloads that share most: multi-turn chat (the prefix grows by one turn), agents (every tool call re-sends the whole context, so hits approach the whole prompt and the cache must survive the tool's latency), parallel samples (`n` outputs per prompt, the groups of 8.5 and the best-of-`n` of Chapter 9, forked with copy-on-write), and the shared-prefix attention kernel that reads the prefix's cache once for all `n` rows.
- Predicting the hit rate: the exact oracle at unbounded capacity, Che's approximation for least-recently-used eviction, and the first-order model of the time to first token saved.
**Derivation:** Che's approximation. For items with request rates `λ_i` under least-recently-used eviction with capacity `C`, the hit probability of item `i` is about `1 − e^{−λ_i T_C}`, where `T_C` solves `Σ_i (1 − e^{−λ_i T_C}) = C`; the expected prefill saved per request is the hit length, and the time to first token falls by about `t_p(n) − t_p(n − hit)`. Smallest case: two prompts that share 512 of 1,024 tokens, where the second computes 512 tokens (plus the last one) instead of 1,024.
